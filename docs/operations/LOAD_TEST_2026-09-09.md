# Informe de prueba de carga: 2026-09-09

## Alcance

Se ejecutó una carga escalonada contra `POST /analizar-imagen-publico` usando una única imagen JPEG de prueba autorizada. La prueba generó 15 análisis reales en cuatro escalones: `1`, `2`, `4` y `8` peticiones concurrentes. Cada escalón lanzó tantas peticiones como su nivel de concurrencia y esperó a que todas terminaran antes de continuar.

La prueba no cambió configuración, no reinició PM2, no borró claves Redis y no mezcló la cola asíncrona de jobs completos con el camino síncrono.

## Resultado funcional

- 15/15 respuestas HTTP `200`.
- 15/15 análisis terminaron en estado `completado`.
- 0 respuestas `4xx`, `5xx` o errores de red.
- 0 rechazos por capacidad durante la prueba.
- PM2 permaneció `online`, con 0 reinicios en todos los procesos observados.
- Bull DB2 terminó con `waiting=0` y `active=0`.
- El contador `failed=3` permaneció estable; son trabajos históricos (`29`, `33` y `37`), no generados por esta prueba.
- MongoDB permaneció conectado y el health check final fue correcto.

## Cuellos de botella detectados

### 1. Arranque en frío del ML

La primera petición tardó `14,8 s`; las siguientes warm se movieron entre aproximadamente `0,8 s` y `3,1 s`. El primer análisis debe separarse siempre del p95 warm.

Mejora prioritaria: readiness que no anuncie capacidad completa hasta calentar el modelo, una petición de warm-up controlada al arrancar y métricas separadas de cold start e inferencia warm.

### 2. Memoria de Embassy y presión del host

Embassy subió hasta aproximadamente `302 MiB` durante la tanda y el host solo conservó unos `595 MiB` disponibles, con swap ya usada. Aumentar procesos o crear un cluster de workers Sharp ahora podría empeorar la situación aunque aumente la concurrencia teórica.

Mejora prioritaria: reducir buffers y payloads retenidos, medir RSS por etapa, mantener Sharp serial hasta una prueba sostenida y no multiplicar Embassy/Sharp sin presupuesto de memoria.

### 3. Stream Redis de red superior

Redis usaba aproximadamente `410 MiB`, pero las colas Bull no eran la causa:

- DB2: aproximadamente `2,6 KiB` reportados por clave.
- DB3: aproximadamente `1,3 MiB` reportados por clave.
- DB1: la clave `dragon3:stream:req:superior` ocupaba aproximadamente `429,5 MiB`.
- El stream tenía 96 entradas, 7 pendientes y lag 0.
- El payload serializado de esas entradas sumaba aproximadamente `159 MiB`; contiene campos `binario` y entradas individuales de hasta aproximadamente `33 MiB`.

El código actual de `QueueManager.publish()` hace `XADD` del payload completo sin `MAXLEN` y sin separar binarios. Este es el cuello estructural más importante encontrado por la prueba y no se resuelve aumentando concurrencia.

Mejora prioritaria: publicar en Redis solo metadata y una referencia a almacenamiento temporal controlado; definir retención y `MAXLEN` por stream; revisar el tratamiento de los 7 pendientes antes de aplicar trimming; configurar alertas de memoria, antigüedad y pending entries. No ejecutar `DEL` o `XTRIM` sin una ventana y una política de recuperación aprobadas.

Tras la revisión de arquitectura, el stream pertenece al runtime legacy de Red Superior y no al flujo actual de células Dragon3. El flujo actual usa Bull DB2/DB3. Se debe desactivar el publisher legacy en producción y conservar límites defensivos para cualquier activación futura.

## Remediación aplicada

- `LEGACY_STREAMS_ENABLED=false` quedó aplicado en Embassy y en el worker async de PM2.
- `QueueManager` quedó protegido con `MAXLEN` y límite de payload para cualquier activación explícita futura.
- El stream legacy `dragon3:stream:req:superior` fue respaldado localmente, sin publicar su contenido, y eliminado después de confirmar que no tenía consumidores activos.
- Redis pasó de aproximadamente `410 MiB` a `250 MiB` usados.
- La E2E posterior confirmó HTTP `200`, estado `completado`, explicación presente, Bull vacío y ausencia de recreación del stream.

### 4. Observabilidad por worker PM2

Las métricas Prometheus del backend se mantienen en memoria por proceso. Consultar `/metrics` a través de un worker del cluster no representa automáticamente la suma de las dos instancias: durante la carga el contador visible mostró solo parte de las peticiones.

Mejora prioritaria: agregar métricas por proceso con `instance` estable o usar un collector/agregador compatible con PM2 cluster antes de declarar SLO globales.

## Decisiones que no recomienda esta prueba

- No recomienda crear todavía un cluster paralelo para Sharp.
- No recomienda subir `QUEUE_CONCURRENCY` como respuesta a esta tanda.
- No demuestra capacidad Enterprise sostenida durante 30 minutos.
- No demuestra comportamiento con imágenes grandes, mezcla de formatos ni Redis bajo fallo.

La política actual de separar células Sharp y procesarlas con worker serial queda respaldada: durante esta carga no hubo errores, reinicios ni acumulación de la cola. El siguiente aumento de capacidad debe atacar primero el payload binario del stream y el arranque frío del ML.
